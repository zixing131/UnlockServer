# v2.3.1 蓝牙稳定性修复与验证

对应 [issue #14](https://github.com/zixing131/UnlockServer/issues/14) 及后续补充。修改的是 `UnlockServer.Wpf`；历史 WinForms 项目未改。

## 已修复的代码问题

- **三分钟暂停后倒计时卡死**：后台 Tick 持有状态锁并同步等待 UI；UI 倒计时回调又等待状态锁，形成互相等待。现在 UI 更新异步投递；倒计时回调只提交带代次的取消请求，锁屏/解锁由后台重新检查条件后执行。
- **关闭搜索窗口即失去信号**：Closing 和 Dispose 重复释放共享扫描引用，误停主监控。现在启停和释放幂等。搜索窗口临时申请全类型扫描，过滤仅影响列表，关闭后恢复主监控需要的扫描类型。
- **过滤无效 / RSSI 突发刷新**：原列表未过滤缓存设备，还共享后台修改的可通知模型，并逐条广播投递 UI。现在每 500ms 获取最新快照，更新 UI 自己的模型，同时应用类型和名称筛选。
- **扫描静默后不恢复**：原恢复逻辑只检查 Stopped/Aborted，且超出短暂宽限后禁止重试。现在也检查持续无广播，每次恢复至少间隔 30 秒，并忽略已停止 watcher 的迟到事件。恢复不会更新设备 LastSeen，也不会无限延长离开判断。
- **旧信号误判**：DeviceWatcher 的 Added 缓存、手动 MAC、连接轮询均不再伪造新的 RSSI 时间戳。停止扫描清除连接缓存；锁屏时也必须有新鲜观测或当前连接，才能自动/点击解锁。
- **监控启停竞态**：每轮监控有独立取消令牌，停止后延迟任务不会重新启动；倒计时执行前检查设备是否返回，旧提示的取消不会影响下一次提示。

没有找到一个固定“11 分钟”触发器；代码缺陷能解释关闭窗口后扫描中止和长期静默，但不能仅凭代码证明所有蓝牙驱动上的同一时间点问题已经消失。

## 自动验证

2026-09-24 验证环境：macOS 的 .NET 8 SDK；Parallels Windows 11 ARM64 内的 Visual Studio 2022、.NET Framework 4.8。

```powershell
# Windows：生成 WPF 和 x64 凭据提供程序
powershell -NoProfile -ExecutionPolicy Bypass -File scripts/build-wpf.ps1 -WithProvider

# Windows：针对实际编译出的 BluetoothService 做验证
powershell -NoProfile -ExecutionPolicy Bypass -File scripts/test-windows-service.ps1

# macOS / Windows，有 .NET 8 SDK 即可；链接实际决策与列表代码
# 系统锁屏、凭据、蓝牙和 Dispatcher 使用可控替身
dotnet run --project tests/UnlockServer.RegressionTests
```

- WPF Release 编译成功。
- x64 Provider Release 编译成功；Provider 源码未修改。
- 8 个回归场景通过：手动解锁冷却到期且蓝牙未返回、倒计时结束时设备返回、持锁期间取消提示、旧取消回调、扫描恢复宽限到期、锁屏时旧 RSSI 不允许解锁、快速启停、搜索窗口引用/过滤/快照隔离。
- Windows 实际服务验证通过：引用计数、不可变缓存快照、元数据不刷新信号时间、手动设备类型、有限恢复宽限、限频重试、停止时清除连接状态。
- 构建有既有 COM 封送警告（MSB3305）；Provider 有既有导出名称警告（LNK4070）。未为这次修复改动自启 COM 接口或 Provider 导出。

Windows 服务验证会短暂尝试启动 BLE 广播 watcher，但不连接设备、不锁屏、不安装凭据提供程序。它证明恢复代码可执行，不证明实际广播接收或物理距离判断已经验证。

## 实机回归清单

测试包面向 Windows x64。虚拟机是 ARM64，因此这里仅完成编译与上述测试，没有安装 x64 Provider 到 ARM64 系统，也没有验证系统登录流程。

先退出旧程序，备份原程序目录及配置；将测试包解压到独立目录。如要沿用配置，复制原来的配置文件；不要同时运行两个版本。x64 系统使用本机解锁时，可按 README 的流程启用/更新本机解锁组件。

1. 绑定 BLE 设备，连续运行至少 30 分钟（覆盖报告中的约 11 分钟）。设备始终在旁边时观察 RSSI 是否持续变化；在第 10、15、25 分钟打开、拖动、关闭搜索窗口，关闭后主界面仍应更新。
2. 在搜索窗口反复切换“全部 / 经典 / BLE”，结合名称搜索检查结果；打开关闭 20 次，主监控不应停止；拖动后不应冻结或连续回放积压的旧数值。
3. 让蓝牙离开触发锁屏，20 秒内手动解锁，确认“暂停自动锁屏 3 分钟”。整个三分钟保持设备离开，到期后应按配置倒计时并实际锁屏，界面仍可操作。启用“仅空闲时锁定”时需满足空闲秒数；“不干预手动解锁”也会按原规则抑制锁屏。
4. 再做一次三分钟测试，但期间让设备回来后离开。结果应符合相同规则；另在倒计时结束前让设备回来，应撤销锁屏。点击取消应取消本次操作。
5. 蓝牙设备关机后应在信号超时、恢复宽限和锁定延迟后被判定离开；不能因重启扫描回放缓存而重新显示靠近。然后打开设备，确认重新检测成功。
6. 关闭/打开 Windows 蓝牙、睡眠/恢复后检查能否恢复扫描，并在日志中查找“恢复 BLE 广播扫描”“重启蓝牙扫描”。确认不是每秒持续重启。
7. 用实际 x64 Windows 账号测试本机解锁、手动锁屏规则及远程桌面切换。锁屏上的“点击解锁”应只在设备有新鲜观测或确实连接时成功。

若仍异常，记录具体发生时间、蓝牙适配器/驱动型号、设备型号、相关规则设置，并保留程序目录下 Logs 对应时间段日志，便于区分设备停播、驱动停止和应用扫描状态。
